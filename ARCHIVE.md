**2026-09-16 update (even later) — concrete demo project defined: world-model veto for unsafe action chunks, industrial-hazard framing.**

Fits directly under the "runtime/pre-deployment safety verification" umbrella above — a third concrete instance alongside `ChunkSafetyProcessorStep` (runtime, rule-based) and the sensitivity gate (pre-deployment, model-level): this one is **runtime, learned-world-model-based**, catching a specific class of unsafe action chunk before execution rather than after.

**Goal**: one narrow, demoable proof — a world-model veto that catches an unsafe predicted action chunk before a VLA policy executes it, in a real industrial-risk category (ATEX/LOTO/permit-to-work framing), on real SO-101 hardware. Not a general safety system.

- **Phase 0 (prerequisite, blocked on physical hardware access — see 2026-09-16 entry above re: away from home setup)**: TurboVLA running inference on Jetson Orin NX, controlling SO-101 live. Log inference latency (ms/step), control loop frequency (Hz), memory footprint; same numbers on Mac M5 for comparison. Output: a short table + one video clip. Postable on its own, independent of everything below.
- **Phase 1**: define one narrow, physically-stageable hazard — not all of ATEX/LOTO/permit-to-work at once. Candidate: a taped "restricted zone" on the desk standing in for a LOTO-locked or ATEX-exclusion area; task is picking up a cup; unsafe variant is a proposed trajectory passing through the marked zone. Maps cleanly to a real industrial rule without needing real hazardous equipment.
- **Phase 2 (the core technical piece)**: hook between action-chunk generation and execution — before chunk N executes, roll the predicted resulting state forward through a world model (V-JEPA2 or a "LeWorldModel"-style module) and check it. **Deliberately scope the check itself as dumb-and-simple first** (geometric: does the predicted end-effector position enter the excluded volume) — the trap to avoid is making the world-model prediction sophisticated before the predict→check→veto pipeline works end-to-end at all. Ship the simple version, improve prediction quality as a v2.
  - Thematically adjacent to the world-model future-frame work already done in #4381 (VLA-JEPA causal-context fix) — both touch predicting/using future world-model states — but not the same mechanism or reusable code; don't overstate the connection when writing this up publicly, it's relevant domain experience, not a direct code reuse.
- **Phase 3**: on violation, block the chunk and do something visibly safe (freeze, or replan a non-intersecting chunk). Log every veto event with timestamp + reason (e.g. "predicted trajectory entered exclusion zone at t+Xms") — the log itself is a deliverable, since auditability is a real industrial safety requirement and citing it signals domain understanding, not just ML.
- **Phase 4 (the actual attention-getting artifact)**: 60-90s video — normal pick task, policy nudged toward the exclusion zone, veto triggers, arm stops/replans, on-screen overlay of the logged reason. Pair with a one-paragraph framing citing prior art (verify the "Pre-VLA" citation before using it publicly — not yet confirmed) and grounding the rule in real public standard language (INRS/OSHA/ATEX directive), not generic "AI safety." This is what gets posted on LinkedIn/HF and referenced when messaging `Adil Zouitine` or `Michel Aractingi` (both real lerobot/SmolVLA-affiliated HF people, per the TurboVLA paper's own author list).
- **Phase 5 (credibility metrics, not just a cool video)**: veto latency overhead added per control step (determines production-viability vs. toy); false positive/negative rate on a small test set of trajectories (20-30 trials is enough for a v1); task success rate with vs. without the veto layer on safe trials (proves the veto isn't just making the arm overly cautious).

**Status**: defined, not started. Phase 0 is blocked on the same physical-hardware access gap as the rest of the SO-101/rollout work right now.

- **Demo done, posted on #4241** ([issue-comment 5440577992](https://github.com/huggingface/lerobot/pull/4241#issuecomment-5440577992)). Trained a quick ACT checkpoint (`ravediamond/act_pick_grey_cup`, 20 teleop episodes of a grey-cup pick, dataset `ravediamond/pick_grey_cu__20260821_102040` — a 180-episode 3-cup dataset `ravediamond/pick_cups_all` also recorded but ACT has no language input so a single-cup subset was used). - **Found and fixed a real bug in own `clamp_action_chunk` while building the eval**: absolute bounds were enforced once up front, but the sequential discontinuity/jerk reconstruction rebuilds each step from the previous *reconstructed* value and can walk the trajectory back outside `[min_action, max_action]` with nothing re-checking it (3/100 real faulted chunks still out of bounds after clamping).
